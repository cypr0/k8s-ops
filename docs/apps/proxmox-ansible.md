# Proxmox Ansible

> **Namespace**  automation
> **Source**     plain manifests — no HelmRelease/HelmRepository; a `CronJob` + `ConfigMap` (`kubernetes/apps/automation/proxmox-ansible/app/`)
> **Hostname**   none — no ingress; egress-only toward the physical Proxmox host

## What it does here
A daily `CronJob` that SSHes into the physical Proxmox VE host underlying this cluster and runs an Ansible playbook to harden and maintain it: OS package updates, fail2ban, CIS-flavored `sshd_config`, a Wazuh agent reporting to the in-cluster manager, auditd with command and credential-file auditing for that agent, and vsftpd for a Brother scanner that drops files into Paperless's NFS consume share. A staged CIS Debian 13 rollout runs after all of that ([CIS hardening](#cis-hardening-debian-13-benchmark)). It's the one app in this repo that reaches *outside* Kubernetes to manage the hypervisor hosting the cluster itself.

## Architecture at a glance
- **Depends on:** ExternalSecret `proxmox-ansible-credentials` (1Password item `proxmox`); ConfigMap `proxmox-ansible-playbook` (`kubernetes/apps/automation/proxmox-ansible/app/configmap-playbook.yaml`) which embeds the entire playbook, a key-fixup script, and the run wrapper; Flux `postBuild.substituteFrom: cluster-secrets` for the `SECRET_ALLOWED_IP` value (`kubernetes/apps/automation/proxmox-ansible/ks.yaml`).
- **Depended on by:** Paperless-ngx's scan-to-consume workflow — the vsftpd account and directory ownership this playbook maintains back the NFS path Paperless mounts as its consume share (`kubernetes/apps/paperless/paperless-ngx/app/pvc.yaml`). Wazuh's visibility into the hypervisor also comes from here: the playbook installs the agent, pins it to the manager's version, and registers it as `proxmox.${SECRET_DOMAIN}` (`kubernetes/apps/automation/proxmox-ansible/app/configmap-playbook.yaml`). It previously forwarded raw syslog to Fluent Bit instead; that was removed on 2026-09-20 once the agent shipped the same events decoded — rsyslog itself stays installed, because it writes the `/var/log/syslog` and `/var/log/auth.log` files the agent tails.

## Secrets
One ExternalSecret, `kubernetes/apps/automation/proxmox-ansible/app/externalsecret.yaml`, pulling from 1Password item `proxmox` (no `refreshInterval` set, unlike most other apps in this repo which set `1h` — falls back to the operator default):

| Key | Consumed by |
| --- | --- |
| `PROXMOX_SSH_HOST` | `PROXMOX_SSH_HOST` env var → written into the Ansible inventory as the target host |
| `PROXMOX_ROOT_SSH_KEY` | mounted read-only at `/tmp/ssh/id_rsa`, then repaired by `fix_key.py` before use (see Known quirks) |
| `PROXMOX_ANSIBLE_SSH_PUBKEY` | `PROXMOX_ANSIBLE_SSH_PUBKEY` env var → installed as the `ansible` OS user's `authorized_keys` by the playbook |
| `PROXMOX_ANSIBLE_SSH_KEY` | The `ansible` user's own private key, matching `PROXMOX_ANSIBLE_SSH_PUBKEY` — a genuinely separate keypair from root's, mounted read-only at `/tmp/ssh/ansible_id_rsa` and repaired by `fix_key.py` the same way as root's key |
| `FTP_SCANNER_PASSWORD` | `FTP_SCANNER_PASSWORD` env var → sets the local `scanner` FTP account's password (`chpasswd`, `no_log: true`) |

A fifth value, `ALLOWED_IP`, is not from this ExternalSecret — it comes from the cluster-wide SOPS-encrypted `cluster-secrets` via Flux's `postBuild.substituteFrom` (`${SECRET_ALLOWED_IP}` in `cronjob.yaml`), and feeds fail2ban's `ignoreip` allow-list in the playbook. Never restate its resolved value — cite the `SECRET_ALLOWED_IP` key in `kubernetes/components/sops/cluster-secrets.sops.yaml`.

A sixth, `RPC_ALLOWED_NETS`, follows the same route from the key `SECRET_RPC_ALLOWED_NETS` (comma-separated IPv4 CIDRs: the LAN the cluster's NFS clients are on and the two WireGuard networks). It is deliberately not written in the playbook or in this document; the key was added to the SOPS file with `sops set --value-stdin` so the value never appeared on a command line. The `cluster-secrets.sops.yaml.j2` template only generates `SECRET_DOMAIN`, so this key, like the other custom ones, lives only in the rendered SOPS file; re-rendering the template from scratch would drop it.

## Routing & access
No HTTPRoute — this app is never reached from outside, only reaches out. The CiliumNetworkPolicy (`ciliumnetworkpolicy.yaml`) scopes to the Job's own pods (`batch.kubernetes.io/job-name` exists) and allows egress only to: `kube-dns` (UDP/TCP 53), `world` on TCP 22 (SSH to the Proxmox host — comment points at `SECRET_ALLOWED_IP` rather than a literal address), and `world` on TCP 80/443 (Alpine's `apk add ansible openssh-client` at container start). No SSO/OIDC — this is a backend batch job, not a service with a UI.

## Storage
None. No PVC in this app's directory, and the `automation` namespace is not in any Velero schedule (`kubernetes/apps/velero/schedules/schedule-daily.yaml` only covers `nextcloud`, `paperless`, `open-webui`, `hermes-agent`). The playbook does manage a directory on the Proxmox host's own filesystem (`/rpool/k8s-rwx/paperless-consume`, ownership `3000:3000` to match Paperless's `USERMAP_UID`/`GID`), but that's host config applied over SSH, not a cluster-backed volume — recovery is simply re-running the (idempotent) CronJob.

## Known quirks
- **1Password collapses the PEM private key's newlines to spaces.** `fix_key.py` (`kubernetes/apps/automation/proxmox-ansible/app/configmap-playbook.yaml`) reconstructs the key's line breaks (header/footer/base64 body handled separately) before `ansible-playbook` ever runs — without it, `PROXMOX_ROOT_SSH_KEY` is unusable as an SSH key.
- **`$${VAR}` double-escaping in `run.sh` is load-bearing, not decorative.** Flux's `postBuild.substituteFrom` scans the *entire* rendered manifest text, including what ends up inside the shell script, so a bare `${PROXMOX_SSH_HOST}` there would be treated as a substitution target — and since it isn't a `cluster-secrets` key, Flux would silently replace it with an empty string. Doubling to `$${VAR}` makes Flux pass through a literal `${VAR}` for the shell to expand at runtime. `ALLOWED_IP` is the one exception: it's substituted once, deliberately, at the `cronjob.yaml` env-var level, not doubled.
- **PVE's built-in firewall is deliberately disabled** (`hardening.yml`, "Disable cluster-level PVE firewall" / "Disable node-level PVE firewall" tasks) — per its inline comment, it "caused a full lockout when allowed_ip was stale." Protection is instead layered as iptables rules in `/etc/network/interfaces`, fail2ban, and OPNsense. Anyone looking for firewall rules in the PVE UI itself will find none by design.
- **A prior playbook version blackholed host→Kubernetes traffic (including NFS) after a Proxmox reboot**, by forcing a route via OPNsense that raced the kernel's own connected route on `vmbr1` and won. `hardening.yml`'s rsyslog section carries an explicit comment not to re-add that route.
- **Root→ansible-user handoff: implemented and verified live 2026-08-16.** The `ansible` OS user was always provisioned (pubkey, passwordless sudo) but never actually connected to — `run.sh`'s inventory used to hardcode `ansible_user=root` for every task, unconditionally, on every run. Fixed across three PRs, each surfaced by actually running the playbook against the real host rather than by inspection alone:
  - **[#70](https://github.com/cypr0/k8s-ops/pull/70)** split `hardening.yml` into a root-only bootstrap play (create/repair the `ansible` user) and a second play running everything else as `ansible` via sudo — a broken `ansible` account now fails that second play loudly instead of silently falling back to root. Its first draft wrongly assumed `PROXMOX_ANSIBLE_SSH_PUBKEY` was the public half of `PROXMOX_ROOT_SSH_KEY`; live inspection of `/home/ansible/.ssh/authorized_keys` disproved that (a distinct `ansible@proxmox` ed25519 key, unrelated to either of root's own `root@proxmox` keys) — corrected in the same PR by generating a real dedicated keypair and adding its private half as `PROXMOX_ANSIBLE_SSH_KEY`.
  - **[#71](https://github.com/cypr0/k8s-ops/pull/71)** — the first live test run authenticated successfully as `ansible` but then failed with "Failed to create temporary directory": years of root-only runs had left `/tmp/.ansible/tmp` `0700` root-owned, so the unprivileged `ansible` user couldn't create its own scratch subdirectory inside it. Fixed by removing the `ANSIBLE_REMOTE_TMP` override entirely and letting Ansible fall back to its own per-user default (`~/.ansible/tmp` — separate homes for root and ansible, no shared path to collide on).
  - **[#77](https://github.com/cypr0/k8s-ops/pull/77)** — the next test run got past authentication and temp-dir creation, then failed with `sudo: not found`: this host had always been administered as root directly, so the `sudo` package itself was never installed. Fixed by adding an `apt` task to the bootstrap play.
  - A fourth manual run (`kubectl create job --from=cronjob/proxmox-ansible ...`) completed with **zero failures on both plays** (`proxmox-host-root: ok=5, changed=1, failed=0`; `proxmox-host-ansible: ok=45, changed=6, failed=0`) — package updates, fail2ban, sshd hardening, syslog forwarding, and vsftpd all applied successfully running as the unprivileged `ansible` account. `hardening.yml`'s hardened `sshd_config` still keeps `PermitRootLogin prohibit-password` for the bootstrap play's sake (its own inline CIS 5.2.10 comment) — root access is now used for exactly four tasks per run, not the whole playbook.
- **The DNAT/routing `lineinfile` tasks in `hardening.yml`** (e.g. correcting a `192.10.100.1` typo, fixing `post-down` to use `-D` not `-A`) are one-time historical fixups now re-asserted idempotently on every run, not general-purpose network config — don't assume they document the "intended" network layout from scratch.

## Common operations
- Manually trigger a run outside the schedule: `kubectl create job --from=cronjob/proxmox-ansible proxmox-ansible-manual-$(date +%s) -n automation`.
- Dry run (reports what would change, touches nothing): same, but with `ANSIBLE_CHECK=1` added to the Job's environment, which makes `run.sh` pass `--check --diff`: `kubectl create job --from=cronjob/proxmox-ansible proxmox-ansible-dryrun-$(date +%s) -n automation --dry-run=client -o json | jq '.spec.template.spec.containers[0].env += [{"name":"ANSIBLE_CHECK","value":"1"}]' | kubectl apply -f -`. Check mode skips `command`/`shell` tasks, so it covers the file, copy, lineinfile and apt changes but not what the shell tasks do (the PVE firewall files, `agent-auth`, `chpasswd`); the read-only commands whose output later tasks read carry `check_mode: false` so the dry run does not trip over its own skips.
- Give `phiros-cmd` its password (once, after the first run that created the account): `ssh root@<host> passwd phiros-cmd`. The playbook creates the account locked and never manages the password; it is only used by `sudo`, SSH accepts keys only.
- Suspend the schedule: `flux suspend kustomization proxmox-ansible -n automation` (the Kustomization lives in the `automation` namespace, not `flux-system`). A plain `kubectl patch cronjob ... suspend=true` did **not** hold on 2026-10-11: it was `false` again after the reconcile that followed a merge (observed once; the mechanism was not investigated, so don't rely on it either way). `flux resume kustomization proxmox-ansible -n automation` undoes it.
- Deploy order when a change needs a new `cluster-secrets` key: Flux must have applied the Secret before it renders this app, otherwise `${SECRET_...}` becomes an empty string. `flux reconcile kustomization cluster-apps -n flux-system --with-source`, then `flux reconcile kustomization proxmox-ansible -n automation --with-source`. The RPC lockdown fails loudly on an empty value and changes nothing.
- Update the playbook itself: edit `hardening.yml`/`run.sh`/`fix_key.py` in `configmap-playbook.yaml`, commit, push — the ConfigMap is mounted fresh into the next Job pod, no restart mechanism needed.
- Rotate a credential: update the 1Password item `proxmox`, then `kubectl annotate externalsecret proxmox-ansible-credentials -n automation force-sync=$(date +%s)` (no `refreshInterval` is set on this ExternalSecret, so don't assume it'll pick up the change on its own within a bounded window).
- Check the last run's result: `kubectl logs -n automation job/<latest-job-name>` — `run.sh` echoes key diagnostics (Ansible version, SSH key line count, inventory host) before invoking `ansible-playbook`.

## CIS hardening (Debian 13 benchmark)
Staged, so that each step can be checked before the next one is applied. `cis.yml` (a play for the `ansible` connection, imported at the end of `hardening.yml`) holds the wave switch `cis_waves` and the admin account; each wave is its own task file. It runs only after the maintenance play succeeded, so a problem in a wave cannot stop the nightly updates, and the Job still fails loudly (visible in `kubectl get jobs`).

**Where it comes from and how it is scored.** The control selection follows the `ansible-debian-cis` role (`roles/cis_debian13`, Nextcloud *Repos* folder), but that role is **not run** here: on a hypervisor several of its remediations would break the host (UFW's forward-deny against the iptables NAT in `/etc/network/interfaces`, removing NFS/FTP, an sshd drop-in that this host's own `sshd_config` would ignore, wholesale rewrites of `/etc/pam.d/common-*`). Each wave is a hand-picked, Proxmox-adapted port. The scorer is the **Wazuh SCA policy `cis_debian13`** on the agent `proxmox.${SECRET_DOMAIN}`, not Ansible: it is independent of what the playbook believes it did. Control numbers in the playbook comments are the Wazuh policy's; the role's differ in places (e.g. `PermitRootLogin` is 5.1.20 in Wazuh, 5.1.21 in the role).

### RPC/NFS ports: internal networks only
Requirement: rpcbind (111), nfsd (2049), mountd (20048), statd (20049, 20050) and, added later the same day because nothing here uses SPICE, the SPICE proxy (3128) answer the LAN and the two WireGuard networks, nobody else.

**What was measured on 2026-10-11** (the "Exposure report" task of `cis.yml`, live on the host):
- IPv4 was already closed to the internet: an INPUT drop on the uplink for these ports (TCP and UDP) and a PREROUTING DNAT that hands everything but 22 and 8006 to OPNsense. Probed from outside: no answer.
- **IPv6 is active**, contrary to what was assumed: the uplink and `vmbr0` have a global address, the uplink has an IPv6 gateway, and Wazuh's inventory lists IPv6 DHCP as enabled on them. `ip6tables -S INPUT` had **no rule at all** (policy ACCEPT), and rpcbind, mountd and statd listen on `[::]` for TCP and UDP. Whether they were reachable from the internet over IPv6 depended on the upstream filtering, which nothing in this repository controls. `sshd` is IPv4-only (`AddressFamily inet`), so 22 is not affected.
- Also on `[::]`/`*`: `spiceproxy` 3128, which IPv4 hides behind the DNAT but IPv6 does not, and `pveproxy` 8006 (open on IPv4 as well, by design, not part of this). 3128 joined the port list in #176 (live since 2026-10-11, see below).

**What it does.** `cis_rpc_lockdown.py` (installed as `/usr/local/sbin/cis-rpc-lockdown`) keeps one chain `CIS-RPC-LOCKDOWN` per address family (iptables and ip6tables) and a jump to it from INPUT for TCP and UDP on those ports. In the chain: loopback and the allowed networks `RETURN`, everything else is `DROP`. IPv6 allows only loopback and link-local, because there are no internal IPv6 clients. It only ever *narrows* INPUT: it never ACCEPTs, never edits another rule, and refuses ports 22 and 8006, public source networks and an empty allow list. Forwarded traffic (DNAT to OPNsense, VM to VM) does not pass INPUT and is untouched. The chain is replaced in one `iptables-restore --noflush` transaction and the jumps are inserted last, so it is never half-written; a missing chain fails open, not closed.

**Safeguards before it changes anything** (only when a run would actually change something, so the nightly no-op run cannot start failing because of an old connection): none of the host's own private addresses may be outside the allowed networks, and no TCP peer outside them may be connected to one of the ports right now (an IPv4 client of a dual-stack socket is recognised as such). Either refuses the run with exit 2 and a message naming the peer; nothing is loaded. An empty `RPC_ALLOWED_NETS` stops the play before anything is installed. The checking `apply` runs **before** the unit is installed and started, on purpose: starting the unit runs `apply --skip-checks`, so with the unit first the checks were bypassed and a connected stranger was cut off while the play reported success (reproduced in a systemd container on 2026-10-11, after #174 was merged and before its first real run; fixed in the follow-up). A refusal now leaves the script and configuration on the host, but no loaded rules, no unit and nothing enabled.

**Kept out of the log.** The Job log goes through Fluent Bit to Loki, so the networks are not printed: the configuration task has `diff: false`, `status` runs with `--summary`, `apply` prints only per-family verdicts. They do appear in a refusal message, because that is when they are needed.

**Boot.** `cis-rpc-lockdown.service` (oneshot, `RemainAfterExit`) loads the rules at boot with `--skip-checks` (nothing is connected yet and the interfaces come up in no fixed order). It is deliberately not ordered before `network-pre.target`: on a hypervisor an ordering cycle is resolved by dropping a job, which could be `networking.service`. For the few seconds after boot IPv4 stays covered by the existing DNAT and INPUT drops.

**Off switch, from Git.** `cis_rpc_lockdown_state` in `cis.yml` is `present` or `absent` (anything else stops the play before it touches the host). `absent` takes the rules out, stops and disables the boot unit, then deletes the unit file, the configuration and the script; change it, merge, and the next run (nightly or a manual Job) does it. It needs neither `RPC_ALLOWED_NETS` nor a working configuration file. It **opens the ports again** to whatever the rest of INPUT lets through, and has no pre-flight check for that on purpose: asking for `absent` is the decision. On a host where nothing is installed it changes nothing. It asks `iptables` and `ip6tables` directly whether the chain is gone, before it deletes any file, so that it fails loudly rather than reporting an `absent` that is not one. The one case it cannot repair by itself: if the script has been deleted by hand while the rules are still loaded, the play fails at that check and keeps the configuration; set the state to `present` for one run (that installs the script again), then to `absent`, or remove the chain by hand.

**Emergency, without waiting for a merge**, on the host as root: `systemctl stop cis-rpc-lockdown` (the unit's `ExecStop` removes the rules) or `/usr/local/sbin/cis-rpc-lockdown remove`, which works even when the configuration file is broken or gone. While the state is `present` the next playbook run puts the rules back. Check what is loaded with `/usr/local/sbin/cis-rpc-lockdown status --verify` (exit 1 if it differs from the configuration).

**Dry run** shows the script, the configuration and the unit as they would be written and skips the apply (it would change the live packet filter), so **the first real run is the live change**. Tested before that against real packet filtering in Debian 13 containers: two networks, IPv4 and IPv6, TCP and UDP, allowed and forbidden clients, 22/8006 and an unrelated port untouched, re-apply, widening, refusals leaving the loaded rules alone, tampering detected and repaired, remove, live connections from outside the allowed networks refused, and a port list that changes while the rules are loaded (the new jump goes in before the stale one comes out, so there is never a moment with neither). The `absent` path and the boot unit were tested in a container that runs systemd: dry run changes nothing, a real `absent` with an active enabled unit and no `RPC_ALLOWED_NETS`, a second `absent` that changes nothing, `present` again restoring everything, and a restart of that systemd with the rules removed beforehand so that only the unit can have loaded them. What none of this covers is a reboot of the real host.

**Live since 2026-10-11 (#174, #175, #176).** The run that added 3128 and the Git switch (#176) went through a dry run (four changes: script, configuration, unit description, apt cache) and a real run with `failed=0`; the play's own verification reported `ok` for IPv4 and IPv6. Checked afterwards from outside over IPv4: 22 and 8006 open, 3128 and the RPC/NFS ports unanswered. That says little about 3128, because on IPv4 the DNAT to OPNsense takes it away before the host's INPUT chain sees it. The test that does: new TCP connections from a worker node (a `hostNetwork` pod on `k8s-wrk-0`, source inside the allowed LAN) to the host's LAN address succeeded for 2049, 111, 20048, 20049, 3128 and 8006, and a closed port was refused. What has still not been tested: a connection to 3128 from a source outside the allowed networks (nothing reachable from here comes from one), IPv6 from outside, and a reboot of the host.

### Wave 2: AppArmor utilities (1.3.1.1)
The SCA rule is two `dpkg-query` calls: `apparmor` and `apparmor-utils` both installed. `apparmor` is on the host already (Wazuh's inventory of 2026-09-28 lists `4.1.1-pmx1`); `apparmor-utils` is not. `cis_wave2.yml` checks the live package list and installs it with `--no-install-recommends`, as a matter of course on a hypervisor (the Proxmox build recommends nothing, so today that changes nothing).

**Proxmox builds its own AppArmor.** The pve repository carries `apparmor`, `apparmor-utils`, `python3-apparmor` and `python3-libapparmor`, all `4.1.1-pmx1`, and its `apparmor-utils` depends on `python3-apparmor` of exactly that version. So apt has to take the Proxmox builds and must not mix in Debian's. ### Wave 2: auditd
`cis_wave2_audit.yml` (after the RPC lockdown in `cis.yml`). Decided by the owner on 2026-10-11: the new rules leave the `ansible` account out; the audit log is rotated and bounded; the checks that would halt the host or keep every log forever stay exceptions (below).

**What it does.**
- Installs `audispd-plugins` (6.2.1.1), simulated first and fail-closed like the other installs: only the plugin and `lib*` packages may be new, nothing installed may change or go. The package ships its forwarding plugins switched off and its maintainer scripts only move conffiles (read in a Debian 13 container); no service is started or restarted.
- Sets `max_log_file = 16`, `num_logs = 8`, `max_log_file_action = ROTATE` in `auditd.conf` (at most about 128 MB, oldest file replaced). The numbers are a choice, not derived from this host's disk; the report prints the space left. What happens when the disk is full anyway stays at Debian's values (warn in syslog, then suspend logging).
- Writes `/etc/audit/rules.d/70-cis.rules` and `71-cis.+.rules`, loads them with `augenrules --load`, and on every run compares the loaded rules with the expected keys; a key that is missing triggers one more load, and if it is still missing the play fails. A rules file on disk is not the same as rules in the kernel, and a failed load leaves the file as it is.
- Prints, read only, the events per key since midnight and the room left for the log.

**Why `70-`.** The kernel logs only the key of the first rule that matches an event: measured with two watches on one path, the one loaded first is the only key in the log, and swapping the file order swapped the key. `60-wazuh.rules` already watches `sudoers`, `sudoers.d`, `passwd`, `shadow` and `group` under `audit-wazuh-w`; a CIS rule for the same path that loaded earlier would silently take Wazuh's events away. `augenrules` loads in name order, so the CIS files come after it. Also measured: `auditctl -R` stops at the first line it cannot load, so what is behind a broken line is not loaded.

**Why `71-cis.+.rules`.** The policy's directory rule for 6.2.3.5 and 6.2.3.19 is `d:/etc/audit/rules.d -> r:.+\.rules$`. In the agent's regex dialect `.` is literal and `\.` is any character, so it needs a file name containing the two characters `.+`. With the real agent 4.14.8: `71-cis.+.rules` passes both checks, `71-cis..rules` and no extra file fail. (The other checks write it the other way round and match `70-cis.rules`.) These rules are only in that file, so that no rule is loaded twice; what `auditctl` does with a duplicate was not tested.

**The `ansible` exception** is only for the new rules that log file access, deletions, permission changes and mounts (`auid!=1000`, read from the host's `passwd` at run time, so a changed UID follows). Its commands are still logged: `60-wazuh.rules` has an `execve` rule without that exception (`audit-wazuh-c`), which is what stands in for `sudo NOPASSWD`.

**Wazuh does not alert on the new keys.** The manager's `audit-keys` list only has the five `audit-wazuh-*` keys, `logall` is off and the alert log starts at level 3, so events under `scope`, `access`, `delete` and the rest stay in `/var/log/audit/audit.log` on the host and do not appear in Wazuh. Decided by the owner on 2026-10-12: no new alerts. The volume of events these rules cause on this host was not measured; read the report of the first night before deciding anything about it.

**Switch, from Git.** `cis_audit_rules_state: present|absent` in `cis.yml`: `absent` removes both files and reloads (`60-wazuh.rules` is not touched either way); anything else stops the play.

**Tested.**
- *Playbook:* the real `cis.yml`, wave 2 only, in a Debian 13 container for `linux/amd64` with `--privileged --pid=host --net=host`, so that rules go into the kernel of the throw-away Docker Desktop VM (aarch64; the x86_64 syscall rules load there, whether they fire on the real host was not tested). Dry run changes nothing; `absent` removes the CIS keys and leaves the Wazuh ones; `absent` again changes nothing; a bad state value stops with nothing changed; rules unloaded by hand are loaded again; a key that never loads fails loudly with the Wazuh rules untouched.

### Wave 2: time servers
`cis_wave2_time.yml` (after auditd in `cis.yml`). Decided 2026-10-17: the host takes its time from the same two servers as the Talos nodes (`162.159.200.1` and `162.159.200.123`, `talos/patches/global/machine-time.yaml` and `ntp_servers` in `cluster.toml`) instead of the Debian pool that chrony ships with. **The Wazuh policy has no check for the servers**, only for chrony's user (2.3.3.2, wave 1) and for the service being enabled and active (2.3.3.3), so this changes no score. Both stay `passed`: the file keeps `user _chrony` and the service is running at the end.

**Order, because a host without a time source is worse than one with the wrong source.**
1. The servers go into `/etc/chrony/sources.d/10-cloudflare.sources` and `chronyc reload sources` loads them without a restart; the pool keeps working.
2. The run waits (default 12 times 5 seconds) until every new server has answered at least once (`reach` not zero in `chronyc -c sources`).
3. Only then the `pool` and `server` lines in `chrony.conf` are commented out (marker `# disabled by proxmox-ansible: `) and chrony is restarted.
4. The run waits until `chronyc -c tracking` reports `Normal` again.

If step 2 fails, the new file is removed and nothing else was touched. If step 4 fails, the commented lines are put back, the new file is removed, chrony is restarted and the run fails. Both end in a failed Job, loudly. Steps 2 and 4 happen only in the run that retires the pool: on every later night there is no active pool line, the new servers are the only sources, and a short outage at the far end must not trigger a rollback that would leave chrony with no source at all.

The run stops before changing anything if the state value is unknown, the server list is empty or has duplicates, `chrony.conf` is missing, or it has no active `sourcedir /etc/chrony/sources.d` line (Debian's default; without it the new file would be ignored).

**Not touched:** `sourcedir /run/chrony-dhcp` (servers a DHCP lease hands out, if any) and the files in `conf.d`. The run prints `chrony.conf`'s active lines, `chronyc sources` and the leap status before and after, so the Job log shows what chrony really uses; the first dry run showed the host's `chrony.conf` to be Debian's stock file (one `pool 2.debian.pool.ntp.org iburst` line, the two `sourcedir` lines, `confdir`, plus `user _chrony` from wave 1), as the design had assumed.

**Switch, from Git.** `cis_time_state: present|absent` in `cis.yml`; `absent` removes the file, restores the commented lines and restarts chrony. `cis_time_servers` is the list.

**Tested.** Debian 13 container (arm64) with systemd, chrony 4.6.1 and ansible-core 2.19, the real task file with the variables read from `cis.yml`; chrony ran with `-x`, so the shared kernel clock was not touched. A second container acted as the NTP server.
- Dry run: shows the new file and the `chrony.conf` diff, changes nothing on disk.
- Real run: pool replaced by the server, leap status `Normal`, service enabled and active, chronyd runs as `_chrony`, `user _chrony` still in `chrony.conf` and `conf.d`. Second run `changed=0`.
- Pool already retired and the server paused: `changed=0`, no rollback, the file stays.
- `absent`: `chrony.conf` byte-identical to the state before, file gone, pool sources back.
- Servers unreachable: the run fails after the wait, the file is removed, `chrony.conf` is identical to before, chrony is running.
- Synchronisation fails after the restart (simulated with a `chronyc` wrapper that reports `Not synchronised`): rolled back to a `chrony.conf` identical to before, file removed, chrony running, run failed.
- Empty list, duplicate list, unknown state: stop with nothing changed. No `sourcedir` line: stops with nothing changed.
- With the two Cloudflare servers: both became the only sources and the leap status was `Normal`. That container's network could reach them, and the stock pool line there had already resolved to both among its sources, so this says little about the host.

Real run: `failed=0`, `changed=6` (the three tasks that always report a change, plus those three); the wait for synchronisation needed one retry, which the Job log shows as an error line although the run succeeded. Afterwards chrony used only the two servers (both answered), reference `time.cloudflare.com`, stratum 4, leap status `Normal`, service enabled and active. ### Wave 2: AIDE

**The checks.** 6.3.1 wants `dpkg -s aide` and `dpkg -s aide-common` to report `install ok installed`. 6.3.2 runs `systemctl is-enabled dailyaidecheck.service` and `systemctl is-active dailyaidecheck.timer` and wants `enabled`, `static` or `active`. **What the package would do on its own, and why it is not left alone.** Debian's configuration walks the whole file system with 239 snippets for services this host does not run, and the packaged unit has no limits. On this host that would mean the kernel module trees (68911 files, 5 GB, ten kernels), the Proxmox storage under `/rpool` (the cluster's NFS exports, guest disks) and `/etc/pve`, a FUSE mount whose files change all the time. The role's `defaults/main.yml` records four of eight HPC workers killed for memory by a daily AIDE run over a network file system. **What is watched** (`aide-cis.conf`; the first run on the host recorded **9793 entries**, files, directories and links together: 7480 under `/usr`, 2228 under `/etc`, 57 under `/boot`, 13 under `/home`, 9 under `/root`, 2 under `/var`, and the four links `/bin`, `/sbin`, `/lib`, `/lib64`; an earlier estimate of about 7000 files, made from counts of regular files only, was too low):

**Not watched, on purpose:** the kernel module trees under `/usr/lib/modules`, the Python trees (about 8000 files), `/usr/lib/firmware`, `/var/lib/dpkg`, the rest of `/usr/share`, `/var/log`, `/rpool` and `/var/lib/vz` (guest disks, NFS exports), `/tmp` and the virtual file systems. No times, no inode and no size are compared: packages and daemons rewrite identical files all the time (`pve-daily-update` rewrites `/etc/apt/apt.conf.d/76pveproxy` every morning). The checksum covers the content of a file; mode, owner, type and link target cover the rest.

**Overlap with Wazuh.** The agent's own file monitoring (read from its `ossec.conf` on 2026-10-17) already covers `/etc`, `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin` and `/boot` every 12 hours. AIDE does not replace it and does not alert; what it adds is the libraries, the Proxmox code, the login material of root and the accounts, and a baseline that only changes when somebody accepts it. The largest tree it reads, `/boot` (1 GB in 49 files), is one that Wazuh already reads every 12 hours.

**How it runs.**
- The package's own timer, with a drop-in: 02:30:00 local time (the host is on Europe/Berlin) plus up to 15 minutes of random delay. The maintenance Job runs at 03:15 UTC (05:15 local time), and in `systemctl list-timers` of 2026-10-17 no other systemd timer was due between 01:00 and 03:00; the times of the cron jobs in `/etc/cron.d` (`vzdump`, `zfsutils-linux`, `e2scrub_all`) were not looked at.
- The service has a drop-in: `Nice=19`, `IOSchedulingClass=idle`, `CPUWeight=10`, `MemoryHigh=256M`, `MemoryMax=512M`, `TasksMax=64`, `TimeoutStartSec=3600` (`RuntimeMaxSec` has no effect on a oneshot unit, systemd says so in the journal), and `ExecStopPost=/usr/local/sbin/cis-aide summary`.
- The packages are installed after an `apt-get --simulate` that must show only the expected new packages (a measured list, anything else, any version change and any removal stop the run), **without recommends**: with them apt adds a mail server, cron and perl. In a clean container the plan is five packages (`aide`, `aide-common`, `liblockfile-bin`, `liblockfile1`, `libext2fs2t64`); on the host a read-only simulation showed `aide` and `aide-common` only, with or without recommends.
- The play builds the baseline (`cis-aide init`, under `systemd-run` with the same kind of limits), stamps it with the checksum of `aide-cis.conf`, and then runs **one real check** the way the timer will, so that a unit that cannot run stops the play and does not fail unnoticed at 02:30.
- `cis_aide_state: present|absent` in `cis.yml`. `absent` stops and disables the timer, removes the drop-ins, the settings block, the configuration, the stamp and the helper; the packages, the database and the logs stay (6.3.1 keeps passing, 6.3.2 fails again).

**Logs, and why none can fill the disk.**
- `aide.log` is written and rotated by the packaged script itself (`savelog`, seven generations, gzip). Measured over eleven runs with changes: seven files, 7.7 KB in total. So there is no logrotate file to add.
- `aideinit.log` and `aideinit.errors` are overwritten at every init.
- The journal gets exactly one line per run: `aide-check result=no-differences|differences|error|no-report service=... aide_exit=... entries=... added=... removed=... changed=... attributes_added_or_removed=... baseline_sha256=... seconds=... peak_memory_mb=... cpu_seconds=...`. The last two make the load readable from the journal alone.
- The database is one file of 357 KB on the host (9793 entries; the container fixture had 80 KB for 2300), and the new one that every check writes next to it is overwritten each night: 714 KB in `/var/lib/aide` in total.
- No mail (`SILENTREPORTS=yes`), although the host has a mail transport.
- Temporary directories that an aborted run leaves in `/var/lib/aide` are removed after seven days by the summary step; fresh ones and links are left alone.

**Reports, and the baseline.** `COPYNEWDB=no`: the baseline changes only when somebody runs `cis-aide accept --yes` (without `--yes` it shows what it would accept and changes nothing). The same differences are therefore reported every night until then, which is deliberate: a baseline that follows the file system silently would forgive the very change it is for. On the host: `journalctl -u dailyaidecheck.service -o cat | grep aide-check` for the history, `cis-aide last` for the last report, `cis-aide check` to run one now, `cis-aide status`.

**Quirks, measured.**
- AIDE does not count a file capability that was **removed** as a difference: exit code 0 and one line before the report (`Entry ... in databases has different attributes: -caps`). An added capability showed up as the same kind of line, in a run that also had other differences. `cis-aide` counts these lines and puts the number in the journal line and in `cis-aide last`.
- The packaged units refuse a second start for 60 seconds (the buildcache unit that the check requires) and for two hours (the check itself), which would make systemd turn the timer's start away after a manual check. `cis-aide check` clears both counters afterwards.
- The helper is mode 0755, not 0750: `ExecStopPost` runs as `_aide`, and with 0750 the unit failed with status 203/EXEC although AIDE itself had run. Found by starting the service in a test.
- A change of `aide-cis.conf` in Git rebuilds the baseline **from the current state**, so any difference that is pending at that moment is accepted with it. Look at `cis-aide last` first.
- Files that the play itself writes (the drop-ins, `/etc/default/aide`, the other waves' files) are part of the baseline; a later change of them through Git shows up as a difference until it is accepted.
- In `/etc/pve` the allow-list is one negative rule with a lookahead. Two obvious forms (positive rules first and the blanket exclusion after, or the other way round) admitted nothing, measured. The rules use `\z` as the end-of-string anchor instead of a dollar sign, because Flux substitutes dollar signs in the ConfigMap.

### Wave 3: SSH access list
`cis_wave3_ssh.yml` (after the time servers in `cis.yml`). Wazuh SCA 5.1.4 reads `sshd -T` and wants an `AllowUsers`, `AllowGroups`, `DenyUsers` or `DenyGroups` line. Decided 2026-10-17: `AllowUsers root ansible phiros-cmd`. The nightly run connects as `root` (bootstrap play) and as `ansible` (everything else), `phiros-cmd` is the human admin; the scanner account is FTP only and stays off the list. `PermitRootLogin` stays `prohibit-password` (5.1.20 stays `failed`, as decided).

**Where the list lives.** In the drop-in `/etc/ssh/sshd_config.d/10-cis-allowusers.conf`. The `sshd_config` that `hardening.yml` deploys ends with `Include /etc/ssh/sshd_config.d/10-cis-allowusers.conf`, by that one path and not a glob, so no stray file in the directory is ever read. OpenSSH 10.0p1 (Debian 13) accepts an `Include` of a file that does not exist: `sshd -t` returns 0 and `sshd -T` shows no list. `sshd -t -o "Include ..."` is not supported, so a candidate cannot be validated on its own.

**The first run changes `sshd_config` and restarts sshd twice.** `hardening.yml` adds the `Include` line, and its existing handler restarts sshd, as for every change to that file; then wave 3 does its own change, probe and restart. Established sessions survive a restart (`KillMode=process`; in the test the Ansible connection stayed usable across it).

**Order in a run that changes the list; a night on which the list is already right does none of this (no probe, no restart, no login).**
1. **Probe.** A second sshd on `127.0.0.1` (random port, own host key, a copy of the real `sshd_config` with the new list, `-e` so that its own log lines go to stderr). Every listed account logs in with a throwaway key, then a control: the same daemon with a list that names only a bogus account must refuse the first user and say `not listed in AllowUsers`. The control is what makes "everyone got in" mean something. The real sshd, its configuration and its port are not touched. The probe refuses to run if the copy has a `Match` block, `AllowGroups`, `DenyUsers` or `DenyGroups`, because it does not model them and would otherwise say `ok` where the real daemon says no. It is run from `/scripts` and is not left on the host.
2. Write the drop-in, `sshd -t`, restart sshd (the same commands as the `Restart sshd` handler).
3. **Fresh logins** from the Job pod as `root` and as `ansible`: a new ssh process each, `ControlPath=none`, one attempt each. Ansible's own connection cannot be used for this check: it is persistent, survives the restart, and would report success even if no new login worked. Then `sshd -T` must show exactly the intended list.
4. **Rollback** if anything in 2 or 3 fails: the previous content of the drop-in is put back (or the file removed, if there was none) and sshd is restarted through that same persistent connection, which is still open. The rollback restart happens only if a restart was attempted. Then the run fails.

**Two side effects to know.**
- *fail2ban.* The jail `sshd` bans an address after 4 failures in 10 minutes for 2 hours; its whitelist is loopback and `allowed_ip`, and whether the Job's source address is `allowed_ip` was not checked, so it is assumed not to be. A login refused by `AllowUsers` counts once (measured with the shipped filter in a container). So step 3 makes one attempt per account, at most two failures, and the probe runs on loopback.
- *Wazuh alerts from the probe.* sshd's own lines about the probe daemon stay out of `auth.log`, but PAM writes `session opened/closed for user NAME` for each probe login to syslog directly (measured, `sshd-session` without a PID), and the rules 5501 and 5502 (level 3) alert on exactly that, also for `phiros-cmd`. One burst, only in the run that changes the list, and the reason the probe does not run every night. `wtmp` is not written (checked against a control login with a PTY).

**Switch, from Git.** `cis_ssh_access_state: present|absent` and `cis_ssh_allow_users` in `cis.yml`. The play refuses any list without `root` and `ansible`, with duplicates or with anything that is not a plain account name, and every listed account must exist; nothing is changed in those cases. `absent` removes the drop-in and restarts sshd; access is then limited by the keys alone. By hand in an emergency: remove the drop-in and restart sshd, which is what the rollback does.

**Tested.** A Debian 13 container with systemd, OpenSSH 10.0p1 and `rsyslog` as the host, a second container running Ansible over real SSH as `root` and `ansible` with the same inventory shape as the Job, the real task files from the ConfigMap.

- Rollback: a regression that the open connection hides (the `ansible` key removed after the connection was up) fails at the fresh login, the drop-in is removed, sshd is restarted and running, the run fails. The same with a previous drop-in: its content is restored. ### Quirks of the Wazuh policy
The checks follow the policy's literal rules, which differ from the CIS text in places, so a "correct" configuration can still score failed. Wave 1 mirrors these on purpose, except the ones that no sensible configuration satisfies (5.4.2.4, 5.4.1.4 and the audit checks at the end of the list). Each audit entry below was confirmed with the real agent 4.14.8, not only by reading the policy:
- **5.2.6** needs `timestamp_timeout` in `/etc/sudoers` *and* in a `sudoers.d` file (condition `all`); both get the same value.
- **5.2.7** needs `pam_wheel.so` with both `use_uid` and an explicit `group=`; the role writes a bare `pam_wheel.so`, which would not pass.
- **7.1.10** stats `opasswd` *and* `opasswd.old`; a missing file fails, so both are created.
- **1.6.1** contains a bare `\s` in its regex, so any `/etc/motd` with a space in it fails; only an absent file passes (the CIS text allows that). `/etc/issue` (1.6.2) is left alone: `pvebanner` rewrites it at every boot.
- **2.3.3.2** needs `user _chrony` in `chrony.conf` *and* in a `conf.d` file.
- **5.4.2.4** ("root account access is controlled") joins two rules with `all`: the output of `passwd -S root` must match `root\s*\t*L` (locked) **and** `root\s*\t*P` (password set). Applied to sample `passwd -S` lines for all three states (locked, password set, no password), no state satisfies both, so no host can pass this check. Nothing to do, and no attempt is made to lock root. Confirmed as a policy quirk by the owner on 2026-10-11.
- **5.4.1.4** ("strong password hashing algorithm") joins two rules with `all` on `/etc/login.defs`: a line matching `ENCRYPT_METHOD SHA512` **and** one matching `ENCRYPT_METHOD YESCRYPT`. Debian 13's stock file has a single line, `ENCRYPT_METHOD YESCRYPT` (read in a `debian:trixie` container), which matches only the second rule; a file with one such line passes in neither setting. By the form of the rules only a file holding both lines would match both, a contradictory configuration (which of the two `login.defs` honours was not checked) that is not pursued. Found 2026-10-11 while sorting the remaining checks; no decision by the owner yet.
- **6.2.3.2** (user emulation) and **6.2.3.14** (MAC policy) each have a rule on the output of `auditctl -l`. With the benchmark's rules in the files, the file rules of both checks pass and the `auditctl -l` rule fails (real agent, fed the output the real `auditctl` 4.0.2 printed). The listing differs from what the rule text spells out: it prints `-C uid!=euid` where the rule has `-C euid!=uid`, `-F auid!=-1` where it has `unset`, and a watch path without a trailing slash, while the 6.2.3.14 rule wants one or a literal backslash. That each of these differences is the cause was not isolated one by one. The two checks stay failed; no rules are written for them.
- **6.2.3.15 to 6.2.3.18** (`chcon`, `setfacl`, `chacl`, `usermod`) chain their terms with `&&`, which the agent applies to one line, and one of the terms, `-F auid!=unset`, has no `r:`, so it is compared as a whole line; a line cannot both start with `-a` and equal that term.
